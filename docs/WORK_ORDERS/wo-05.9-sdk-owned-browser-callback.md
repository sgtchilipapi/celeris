# WO-05.9 SDK-Owned Browser Callback And Redirect Flow

## Objective

Make the browser SDK own the hosted-auth callback contract end to end so app frontends do not have to manually parse callback parameters, validate auth state, or exchange auth codes themselves.

This work order closes the gap between the current demo-grade popup flow and the production-grade browser contract implied by the existing browser auth policy model:

- app frontends already register exact `allowedFrontendOrigins` and `allowedRedirectUris`
- the current runtime validates those values before hosted login starts
- the current successful login path still returns to the app through popup `postMessage`
- the current `redirectUri` is therefore more policy than active browser runtime behavior

After this work order:

- the browser SDK owns popup and redirect login completion
- `redirectUri` becomes an actively exercised part of the browser contract
- app frontends can implement `/auth/callback` without custom auth code
- popup mode remains available, but callback handling is still SDK-owned
- the mock frontend uses the callback flow as part of its normal login path

## Scope

In scope:

- browser SDK callback handling as first-class API
- redirect-based hosted login completion
- popup login flow converging on the same callback contract
- SDK-owned auth-code exchange and session persistence
- standalone mock frontend refactor to use SDK callback handling
- test and docs updates required to make callback handling the supported browser contract

Out of scope:

- developer API hardening from `WO-06`
- native mobile callback contracts
- non-browser auth transports
- changing wallet-keyed credits, managed actions, or asset-delivery behavior
- replacing Privy or changing the hosted auth origin

## Dependencies

- `WO-05.6`

## Domain Assumption

Hosted browser auth still runs on `https://auth.celeris.pro`.

The browser frontend still receives only a Celeris auth code and exchanges it for a Celeris player session. It must not receive a raw Privy token as its player API credential.

## Implementation Steps

1. Promote callback handling to an explicit browser SDK contract.
   - Add a callback-oriented API such as:
     - `auth.login({ mode: "popup" | "redirect" })`
     - `auth.handleCallback()`
     - `auth.getSession()`
     - `auth.logout()`
   - The SDK must own:
     - PKCE or equivalent verifier generation
     - login state persistence
     - callback parameter parsing
     - state / verifier validation
     - auth-code exchange
     - player-session persistence and cleanup

2. Make `redirectUri` an active hosted-auth runtime path.
   - Replace the current effective contract where successful browser login is completed only through popup `postMessage`.
   - The hosted auth flow must be able to complete by returning to a registered app callback URI with:
     - a Celeris auth code
     - SDK validation material such as state
   - The callback path must still avoid exposing a raw Privy token to the app frontend.

3. Converge popup and redirect flows on one callback model.
   - Popup mode may still be the preferred desktop UX.
   - However, popup completion must use the same callback semantics as redirect mode rather than remaining a separate one-off transport contract.
   - A good target contract is:
     - hosted auth redirects the popup window to the app callback URI
     - the callback page calls the SDK callback handler
     - if `window.opener` exists, the SDK may notify the opener and close the popup
     - if no opener exists, the callback page completes the login in place and restores the app session

4. Refactor the mock frontend around SDK-owned callback handling.
   - `mock-game-frontend` must provide a real `/auth/callback` browser path.
   - That route may be:
     - an SPA route served by the same frontend bundle, or
     - a dedicated callback page that imports the browser SDK
   - The mock frontend must no longer rely on the current behavior where the homepage remains open and receives the auth code only through popup `postMessage`.
   - The callback path must:
     - call the SDK callback handler
     - restore the Celeris player session
     - navigate the player back to the homepage or game view
     - fail closed with a visible error state when callback validation fails

5. Update local bootstrap and browser auth policy assumptions.
   - `scripts/mock-game-frontend.ts` and `scripts/full-demo.ts` must provision callback URIs that are actually handled by the frontend runtime.
   - Demo docs must stop implying that the configured `redirectUri` is only a validation artifact.
   - Browser auth policy copy in the dashboard and mock frontend docs should reflect that both:
     - frontend origins
     - redirect callback URIs
     are required for hosted login to work.

6. Preserve popup fallback while making redirect mode production-ready.
   - Popup login should remain supported for desktop browsers.
   - Redirect login should become the canonical non-popup fallback for:
     - popup blockers
     - mobile browsers
     - browsers or environments where `window.opener` is unreliable
   - The SDK must make choosing between popup and redirect an SDK-level concern, not app-specific auth plumbing.

7. Rewrite tests and docs around the callback-owned contract.
   - Replace tests that prove only the current popup `postMessage` path.
   - Add coverage for real callback handling through the SDK.
   - Update docs so developers understand that they should mount an SDK-owned callback route, not manually exchange codes themselves.

## Acceptance Criteria

- The browser SDK exposes a first-class callback handler for hosted browser login.
- A registered `redirectUri` is actively used in the supported browser login flow.
- The app frontend does not need to manually parse callback query params or call `/v1/auth/token` directly.
- Popup login and redirect login both complete through the SDK-owned callback contract.
- The mock frontend provides a real `/auth/callback` path and uses it to establish the Celeris player session.
- Successful browser login still yields a Celeris-issued player session rather than a raw Privy token.
- Callback validation fails closed when state, verifier, origin, or code exchange is invalid.

## Unit Test Cases

- Browser SDK callback handling rejects missing or mismatched state / verifier data.
- Browser SDK callback handling exchanges a valid auth code for a persisted Celeris player session.
- Popup mode and redirect mode both reuse the same callback validation and session persistence logic.
- Hosted auth completion never exposes a raw Privy token as the player API credential contract.

## Integration Test Cases

- The standalone mock frontend can complete hosted login through `/auth/callback` and arrive at the authenticated homepage with a valid Celeris session.
- Popup login redirects to the callback route, the SDK completes the exchange, and the opener is updated correctly.
- Redirect login without a popup completes entirely through the callback route and lands the player back in the app.
- A callback URL that is not allowlisted is rejected before hosted login completion succeeds.
- A replayed or verifier-mismatched callback cannot establish a player session.
