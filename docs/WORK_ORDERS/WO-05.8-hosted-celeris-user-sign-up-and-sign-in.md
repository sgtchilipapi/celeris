# WO-05.8 Hosted Celeris User Sign-Up And Sign-In

## Objective

Complete the hosted player-auth model so each Celeris app delegates end-user sign-up and sign-in to `https://auth.celeris.pro`, where Celeris wraps Privy authentication, ensures an embedded wallet exists, and returns a Celeris player session to the app frontend through an auth-code exchange.

This work order closes the remaining gap between the current hosted-auth implementation and the intended product contract:

- app frontends initiate login with Celeris, not Privy directly
- sign-up and sign-in UI runs on the Celeris-controlled auth origin
- Privy performs authentication and embedded-wallet provisioning behind the hosted gateway
- Celeris maps the verified Privy user to one stable shared Celeris user
- the app frontend receives a Celeris session token plus resolved wallet context after exchanging a one-time auth code

It also fixes the current implementation gaps that still make the hosted flow demo-grade:

- shared player identity is still keyed by wallet rather than the real Privy user subject
- the hosted login UI is still email-code-only rather than a real hosted SSO surface
- the popup handoff is not yet bound strongly enough to the originating login request
- player-session lifecycle and auth-origin deployment assumptions are still under-specified

## Scope

In scope:

- hosted Celeris user sign-up and sign-in for browser app frontends
- Privy-backed SSO or configured hosted identity-provider login on `auth.celeris.pro`
- embedded-wallet provisioning or recovery on the hosted auth origin
- stable shared Celeris user identity keyed by the verified Privy subject rather than wallet address
- hardened login-request, auth-code, and player-session contracts
- browser SDK updates required for the final hosted login flow
- standalone demo updates required to consume the final hosted login flow
- tests and docs required to make this the supported browser-login contract

Out of scope:

- developer bearer auth and server SDK work from `WO-06`
- native mobile or non-browser login flows
- non-Privy identity providers
- changes to wallet-keyed payments, managed actions, or asset-delivery semantics

## Domain Assumption

The hosted sign-up and sign-in flow runs only on `https://auth.celeris.pro` and uses the single Celeris-owned Privy app introduced in `WO-05.5`.

This work order assumes:

- developer-owned frontend origins are not allowlisted directly in Privy for browser login
- one or more Privy-hosted SSO providers are configured under the Celeris-owned Privy app
- app frontends receive a Celeris-issued player session after auth-code exchange, not a raw Privy player token for player API use

## Implementation Steps

1. Finalize the browser-facing hosted-auth contract.
   - Preserve the high-level flow:
     - app frontend calls `POST /v1/auth/login-requests`
     - frontend opens hosted login on `https://auth.celeris.pro`
     - Privy sign-up or sign-in completes on the hosted auth origin
     - Celeris verifies Privy identity and ensures the embedded wallet exists
     - hosted auth returns a one-time auth code to the opener
     - frontend exchanges the auth code for a Celeris player session through `POST /v1/auth/token`
   - Do not let app frontends use a raw Privy token as the player API credential.
   - Keep wallet identity derived from the verified hosted auth session rather than request-body input.

2. Re-key shared Celeris identity to the real Privy subject.
   - Replace wallet-derived shared identity such as `privy-wallet:<chain>:<wallet>` with the stable Privy subject or user ID returned by verified Privy auth.
   - `celeris_user` must represent the person or account known by Privy, not the current wallet address.
   - `project_user` membership and player sessions may still store the active wallet principal for an app, but they must point back to the stable shared `celeris_user`.
   - If the same Privy user later recovers or reprovisions an embedded wallet on the allowed chain, Celeris must still resolve the same shared player identity.

3. Replace the hosted auth UI with a real hosted SSO entrypoint.
   - The hosted auth page on `auth.celeris.pro` must use Privy's real browser auth UI or equivalent real Privy browser APIs for configured hosted login providers.
   - Email OTP may remain as an implementation detail only if it is one configured Privy login method on the Celeris-owned origin, but the hosted flow must no longer be hardcoded as an email-only login surface.
   - The developer frontend must not load Privy directly for this flow.
   - Complete sign-up and sign-in entirely on the hosted auth origin before issuing any auth code or player session.

4. Ensure embedded-wallet provisioning is part of hosted completion.
   - After successful Privy authentication, the hosted auth client must verify that the correct embedded wallet exists for the app's allowed chain.
   - If it does not, Celeris must provision or recover it through the hosted Privy flow before auth completion succeeds.
   - Hosted auth completion must fail closed when a verified user cannot produce a supported wallet principal for the app's allowed chain.

5. Harden login-request and auth-code exchange binding.
   - Extend `loginRequest` persistence with the additional binding material needed for the final browser flow, such as `state`, `nonce`, PKCE challenge material, or equivalent one-time verifier data.
   - Bind popup completion and auth-code issuance to the originating login request.
   - Bind auth-code exchange to the expected verifier so replayed, cross-tab, or mismatched completions fail closed.
   - Preserve the exact origin and redirect-URI validation introduced in `WO-05.6`.
   - Expired or consumed login requests and auth codes must remain single-use and fail closed.

6. Make the hosted auth origin and API boundary explicit.
   - Do not rely on relative browser fetches that only work if the hosted auth UI and token API happen to be mounted on the same origin and path layout.
   - Pass the intended auth API base or equivalent explicit runtime contract into the hosted auth client bundle.
   - If the supported deployment keeps hosted auth UI and auth API co-hosted, document that contract explicitly rather than leaving it implicit in the implementation.

7. Tighten Celeris player-session lifecycle.
   - Issue Celeris player sessions only from successful auth-code exchange.
   - Keep player-route authentication based on Celeris-issued sessions, not raw Privy access tokens.
   - Add revoke or logout behavior required by the supported browser SDK flow.
   - If browser storage remains token-based, document the security assumptions clearly; otherwise move to a more secure session transport as part of this slice.
   - Preserve app-level chain checks after the session is resolved.

8. Rewrite the browser SDK around the final hosted flow.
   - `celeris.login()` or the equivalent browser SDK helper must own:
     - login-request creation
     - popup open or redirect handling
     - state or verifier generation and storage
     - hosted auth completion validation
     - auth-code exchange
     - session persistence and logout
   - The browser SDK must validate the hosted auth origin exactly before accepting completion messages.
   - The browser SDK must not expose the hosted Privy token as the player API credential contract.

9. Update the standalone player demo and local bootstrap.
   - `mock-game-frontend` must consume the final hosted auth flow without embedding Privy directly.
   - Demo bootstrap must clearly configure:
     - hosted auth origin
     - allowed frontend origins
     - allowed redirect URIs
     - required Privy runtime settings for hosted sign-up and sign-in
   - Remove any remaining demo copy that implies player login is primarily a local mock flow or that the app frontend itself owns Privy auth.

10. Rewrite tests and docs around the final hosted sign-up/sign-in contract.
   - Replace tests that only prove the synthetic hosted-token shortcut with tests that validate the final hosted contract boundaries.
   - Add coverage for:
     - stable shared `celeris_user` identity based on Privy subject
     - same Privy user resolving to one shared player across wallet reprovisioning on the allowed chain
     - hosted auth completion requiring a valid embedded wallet
     - state or verifier mismatch rejection during code exchange
     - popup completion acceptance only from `auth.celeris.pro`
     - app frontend receiving a Celeris session after auth-code exchange
   - Update docs to describe Celeris-hosted user sign-up and sign-in as the supported browser flow for app frontends.

## Acceptance Criteria

- A Celeris app frontend can initiate end-user sign-up or sign-in by calling Celeris, without embedding Privy directly.
- Hosted browser login runs on `https://auth.celeris.pro` and uses the Celeris-owned Privy app.
- Privy authentication and embedded-wallet provisioning occur only on the hosted auth origin.
- The app frontend receives a Celeris auth code and then a Celeris player session after exchange, rather than using a raw Privy token as the player API credential.
- The same Privy user resolves to one shared `celeris_user` across apps even if the active embedded wallet on the allowed chain is reprovisioned or recovered.
- Hosted auth completion fails closed when:
  - the login request is expired or consumed
  - the origin or redirect URI is not allowed
  - the auth-code verifier or equivalent binding material does not match
  - the Privy-authenticated user cannot produce a supported embedded wallet principal
- The browser SDK and standalone demo both use the final hosted Celeris sign-up and sign-in flow.

## Unit Test Cases

- `PrivyAuthService` resolves a stable shared identity from the verified Privy subject rather than from wallet address alone.
- `AuthGatewayService` issues one shared `celeris_user` for the same Privy subject across multiple logins, including wallet reprovisioning on the allowed chain.
- Login-request creation and auth-code exchange reject mismatched or missing binding material.
- Hosted auth completion rejects users without a supported embedded wallet on the required chain.
- Player-session verification still enforces project and chain scoping after the session is issued.

## Integration Test Cases

- Browser SDK login initiates hosted auth, receives a completion message from `auth.celeris.pro`, exchanges the auth code, and then calls `GET /v1/me` with the resulting Celeris session.
- One Privy user can sign into two different apps and produce one shared `celeris_user` with two distinct app or project memberships.
- A replayed or verifier-mismatched auth-code exchange is rejected.
- The standalone demo signs the player in through the hosted Celeris sign-up or sign-in flow and then executes the existing wallet-keyed player actions with the returned Celeris session.
