# WO-05.7 Real Privy Hosted Auth Integration

## Objective

Replace the temporary mock hosted-auth implementation with real Privy browser authentication running only on the Celeris-controlled auth origin at `https://auth.celeris.pro`.

This work order finishes the auth-gateway slice by closing the remaining gap between the current hosted-login contract and the updated MVP requirement that browser sign-in be backed by Privy's embedded wallets.

The target model after this WO is:

- developer frontends still call `celeris.login()`
- the browser popup or redirect still lands on `auth.celeris.pro`
- Privy UI and wallet authentication run only on the Celeris auth origin
- Celeris verifies the real Privy-authenticated identity and issues the player session
- the runtime has no browser-facing mock hosted-login path such as manual wallet entry or `privy_mock`

## Scope

In scope:

- replacement of the temporary hosted-login mock UI with real Privy integration
- runtime configuration required for real Privy auth on the Celeris-owned auth origin
- Privy-authenticated completion of the auth-code exchange flow introduced in `WO-05.6`
- removal of temporary runtime affordances that let browser login bypass real Privy auth
- local/demo bootstrap changes required to exercise the real hosted-auth path
- tests and docs updates required to make the real Privy flow the supported browser-login path

Out of scope:

- developer bearer auth and server SDK work from `WO-06`
- native mobile auth flows
- non-Privy identity providers
- changes to wallet-keyed payments, managed actions, or asset-delivery behavior

## Dependencies

- `WO-05.5`
- `WO-05.6`

## Domain Assumption

The Privy app used for browser login is the single Celeris-owned app introduced by `WO-05.5`, and `https://auth.celeris.pro` is allowlisted in that Privy app for browser authentication.

This work order assumes that developer-owned frontend origins are not allowlisted directly in Privy for browser login.

## Implementation Steps

1. Remove the temporary hosted-auth mock contract.
   - Remove the runtime path that accepts hosted-login completion through manual wallet entry.
   - Remove any runtime grant type or equivalent browser-login contract such as `privy_mock`.
   - Remove any hosted auth UI copy that asks the player to type a wallet address directly.
   - Test-only doubles may still exist inside tests, but they must not be the runtime default for the standalone demo or local browser-login path.

2. Add real Privy runtime configuration for the hosted auth origin.
   - Define the environment and runtime config required for real Privy login on `auth.celeris.pro`.
   - Fail closed when required Privy auth configuration is missing in runtime modes that advertise browser login.
   - Keep the platform-owned Privy configuration centralized under Celeris control rather than reintroducing per-app ownership fields.
   - Update `.env.example` and local setup docs to describe the required hosted-auth Privy config clearly.

3. Replace the hosted login UI with real Privy authentication.
   - Render the hosted login entry on `auth.celeris.pro` using the real Privy browser SDK or equivalent real Privy browser integration.
   - The developer frontend must not load Privy directly as part of this flow.
   - Complete Privy login entirely on the hosted auth origin before issuing any Celeris auth code or player session.

4. Verify Privy identity and issue the auth code from the hosted gateway.
   - Replace mock wallet capture with real Privy-authenticated identity resolution.
   - Verify the Privy-authenticated wallet principal through the Celeris-owned Privy configuration.
   - Upsert `celeris_user` and `project_user` from the verified identity.
   - Issue the one-time auth code only after successful real Privy verification.

5. Preserve the player-session contract and tighten failure behavior.
   - Keep the browser-facing player API contract introduced in `WO-05.6`: player routes trust Celeris-issued sessions, not raw Privy tokens.
   - Ensure hosted auth completion fails closed when Privy identity verification fails, when no valid wallet principal is present, or when the hosted auth session is otherwise incomplete.
   - Keep project origin and redirect-URI validation unchanged and enforced before auth code issuance.

6. Rewrite local and demo bootstrap around the real hosted-auth path.
   - Update `mock-game-frontend` and `start:full-demo` so the supported local browser-login path exercises real Privy auth, not the hosted mock.
   - If local testing needs a tunnel or explicit auth-origin override, document and bootstrap that path clearly.
   - Remove any README or demo copy that still describes browser login as a mock Privy flow once the real integration lands.

7. Rewrite tests and docs.
   - Update hosted-auth tests so the supported runtime path is real Privy-backed, with Privy SDK boundaries stubbed or adapter-driven in tests as needed.
   - Add coverage that runtime browser auth no longer exposes mock-only grant paths.
   - Document the required Privy config, allowlisting expectation for `auth.celeris.pro`, and how developers consume the browser SDK login flow after this cut.

## Acceptance Criteria

- Browser login through `celeris.login()` uses real Privy auth on `https://auth.celeris.pro`.
- The hosted auth runtime exposes no browser-facing mock login path such as manual wallet entry or `privy_mock`.
- Developer frontends do not embed Privy directly for the hosted browser-login flow.
- Celeris issues player sessions only after real Privy identity verification succeeds on the hosted auth origin.
- Missing or invalid hosted-auth Privy configuration fails closed rather than silently falling back to a mock browser-login path.
- Local and demo documentation describe how to exercise the real hosted-auth flow with the Celeris-owned Privy app.

## Unit Test Cases

- Hosted auth bootstrap fails closed when required Privy runtime config is missing or invalid.
- Hosted login completion rejects requests that do not produce a verified Privy wallet principal.
- The runtime no longer accepts the temporary mock browser-login grant path.
- Player-session issuance still resolves the correct shared `celeris_user` and app/project membership from the verified Privy identity.

## Integration Test Cases

- Browser SDK login initiates a hosted login request, completes through the hosted auth origin, exchanges an auth code, and then calls `GET /v1/me` using the resulting Celeris player session.
- The hosted auth runtime cannot complete browser login by manual wallet entry alone.
- The standalone demo authenticates through the hosted auth origin and then executes the existing wallet-keyed player flows.
- Docs and local setup instructions are sufficient for a developer to configure the Celeris-owned Privy app and exercise the hosted browser-login flow end to end.
