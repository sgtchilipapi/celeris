# WO-05.10 Google SSO And Privy Wallet Provisioning

## Objective

Make hosted player sign-up and sign-in truly SSO by requiring a Google-based login path on `https://auth.celeris.pro`, then having Privy create or recover the embedded wallet for the app's allowed chain before Celeris issues the player session.

This work order closes the remaining product gap after the hosted-auth, hosted-user-auth, and callback slices:

- browser login should feel like real consumer SSO, not an email-code implementation detail
- the supported default player onboarding path must be Google account sign-up or sign-in
- first-time players should not have to understand or provision wallets manually
- Privy should create the embedded wallet after Google authentication
- Celeris should still own the hosted auth origin, session issuance, and shared player identity contract

## Scope

In scope:

- Google account sign-up and sign-in as a supported hosted auth path on `auth.celeris.pro`
- Privy-hosted Google provider usage under the Celeris-owned Privy app
- embedded-wallet creation or recovery after successful Google authentication
- hosted auth UI and copy updates required to present the flow as true SSO
- browser SDK and standalone demo updates required to consume the Google-first hosted flow
- tests and docs required to make Google SSO plus Privy wallet creation the supported browser-login contract

Out of scope:

- developer bearer auth and server SDK work from `WO-06`
- direct Google auth flows outside Privy
- native mobile sign-in surfaces
- adding every possible social provider beyond Google in this slice
- changes to wallet-keyed payments, managed actions, or asset-delivery semantics

## Domain Assumption

The hosted sign-up and sign-in flow still runs only on `https://auth.celeris.pro` and still uses the single Celeris-owned Privy app introduced in `WO-05.5`.

This work order assumes:

- Google is configured as a hosted login provider in the Celeris-owned Privy app
- app frontends still call Celeris rather than Google or Privy directly
- Privy remains responsible for embedded-wallet creation and recovery
- Celeris still maps the verified Privy user subject to the stable shared `celeris_user`
- the app frontend still receives only a Celeris-issued session after auth-code exchange

## Implementation Steps

1. Define Google SSO as the supported hosted browser-login contract.
   - The hosted auth UI on `auth.celeris.pro` must expose a real Google sign-up or sign-in path through Privy.
   - The supported player onboarding copy must describe Google sign-in, not an email-code-only flow.
   - App frontends must continue to call the browser SDK rather than integrating Google or Privy directly.

2. Require the Google provider under the Celeris-owned Privy app.
   - Document the required Privy configuration so the hosted auth origin can present Google login.
   - Fail closed when the runtime is configured to advertise hosted browser login but the required Google-backed Privy configuration is unavailable.
   - Keep all provider ownership centralized under Celeris rather than reintroducing per-app auth ownership.

3. Ensure first-time Google login provisions the embedded wallet automatically.
   - After successful Google authentication through Privy, the hosted auth client must verify that an embedded wallet exists for the app's allowed chain.
   - If the wallet does not exist yet, Privy must create or recover it before hosted auth completion succeeds.
   - The player must not be asked to paste, connect, or manually create a wallet as part of the supported browser-login flow.

4. Preserve stable shared identity across repeated Google logins.
   - The same Google-backed Privy user must resolve to the same `celeris_user` across apps.
   - `project_user` and player sessions may still carry the active wallet principal, but identity stability must come from the verified Privy subject rather than the current wallet address.
   - If Privy reprovisions the embedded wallet on the allowed chain, Celeris must still resolve the same shared user.

5. Keep the SDK-owned callback and session boundary intact.
   - `auth.handleCallback()` and the hosted auth callback flow from `WO-05.9` must remain the only supported browser completion contract.
   - The app frontend must not receive raw Google or Privy tokens as player API credentials.
   - The browser SDK should continue to hide provider-specific details behind the existing Celeris login API.

6. Replace email-first demo assumptions with Google-first hosted auth.
   - Remove hosted auth UI copy that implies email OTP is the primary or only supported browser-login contract.
   - Update the standalone demo and local bootstrap so the intended happy path is Google sign-up or sign-in followed by automatic wallet creation.
   - If email or other providers remain configured in Privy, document them as optional provider configuration rather than the product-default auth contract.

7. Rewrite tests and docs around Google SSO plus automatic wallet creation.
   - Add coverage for first-time Google login creating the embedded wallet before Celeris session issuance.
   - Add coverage for repeat Google login resolving the same shared `celeris_user`.
   - Add failure coverage for missing Google-provider config, failed wallet creation, or unsupported wallet principal resolution.
   - Update docs to describe Google sign-up and sign-in through the hosted Celeris auth gateway as the supported browser-login flow.

## Acceptance Criteria

- A first-time player can sign up through Google on `https://auth.celeris.pro`.
- A returning player can sign in through the same Google account on `https://auth.celeris.pro`.
- After successful Google authentication, Privy creates or recovers the embedded wallet for the app's allowed chain before Celeris issues the player session.
- The app frontend receives only a Celeris auth code and then a Celeris player session after exchange.
- The same Google-backed Privy user resolves to one shared `celeris_user` across apps and repeated logins.
- The supported browser-login flow does not require manual wallet entry, wallet connection, or email-code-only onboarding.
- Missing or invalid Google-provider or wallet-provisioning prerequisites fail closed rather than silently degrading the hosted-login contract.

## Unit Test Cases

- Hosted auth bootstrap fails closed when Google-backed Privy provider configuration required for the supported flow is unavailable.
- Hosted auth completion provisions the embedded wallet when a verified Google-backed Privy user does not yet have one on the allowed chain.
- Hosted auth completion rejects the login when wallet creation or recovery fails.
- The same Google-backed Privy subject resolves to the same shared `celeris_user` across repeated logins.

## Integration Test Cases

- First-time Google login completes through the hosted auth origin, causes Privy to create the embedded wallet, exchanges the auth code, and then calls `GET /v1/me` using the resulting Celeris session.
- Returning Google login reuses the same shared player identity and succeeds without manual wallet steps.
- The standalone demo signs the player in through Google-based hosted auth and then executes the existing wallet-keyed player flows.
- Docs and local setup instructions are sufficient for a developer to configure the Celeris-owned Privy app for Google login and exercise the hosted browser-login flow end to end.
