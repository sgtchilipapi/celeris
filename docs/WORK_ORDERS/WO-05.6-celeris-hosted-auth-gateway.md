# WO-05.6 Celeris-Hosted Auth Gateway

## Objective

Introduce a Celeris-hosted player auth gateway on `https://auth.celeris.pro` so developer apps authenticate players through Celeris rather than embedding Privy directly on developer-owned origins.

This work order changes the browser-facing player auth model from:

- developer frontend obtains a Privy bearer token directly
- developer origin must be allowlisted in Privy

to:

- developer frontend calls `celeris.login()`
- Celeris opens hosted login on `auth.celeris.pro`
- Privy sign-in happens only on the Celeris-controlled auth origin
- Celeris verifies Privy identity and issues the player session used by the player API

The result should be that Privy allowlisting is required only for Celeris-controlled auth origins, not each developer frontend origin.

## Scope

In scope:

- hosted login gateway on `auth.celeris.pro`
- project-level auth configuration for allowed frontend origins and redirect URIs
- popup or redirect-based login initiation from the browser SDK
- login-request validation using `projectId`, `redirectUri`, and request `Origin`
- Privy login on the Celeris-controlled auth origin only
- Celeris-issued player session tokens for browser access to the player API
- shared `celeris_user` identity plus app/project-scoped `project_user` membership records
- mock-game frontend migration from direct Privy-token assumptions to hosted Celeris login

Out of scope:

- native mobile auth gateway behavior
- developer bearer auth beyond any config fields needed to register project origins and redirect URIs
- non-browser player auth transports
- changing wallet-keyed payments, managed actions, or asset-delivery semantics

## Implementation Steps

1. Replace the browser-facing player auth contract.
   - Stop treating the browser player auth contract as “developer frontend presents a raw Privy bearer token to Celeris”.
   - Replace it with “developer frontend presents a Celeris-issued player session created by the hosted auth gateway”.
   - Keep the wallet principal as the product-level player identity after the session is resolved.

2. Add hosted auth-gateway domain and project config contracts.
   - Introduce runtime config for the hosted auth origin, explicitly defaulting to `https://auth.celeris.pro`.
   - Add project/app auth-gateway config fields for:
     - allowed frontend origins
     - allowed redirect URIs
   - Keep `projectId` as the gateway term if desired, but this WO may alias it to the existing `appId` to avoid a repo-wide rename.
   - Do not reintroduce developer-managed Privy ownership fields such as `privyAppId`.

3. Add auth-gateway persistence and core services.
   - Add storage and service contracts for:
     - login requests
     - one-time authorization codes or equivalent one-time handoff artifacts
     - player sessions
     - shared `celeris_user`
     - app/project membership records such as `project_user`
   - Login requests must record:
     - `projectId`
     - initiating origin
     - requested redirect URI
     - state / PKCE material as needed
     - expiry
     - consumed status
   - Player sessions must be independently verifiable by the player API without requiring Privy verification on every player request.

4. Add auth-gateway routes and hosted login flow.
   - Add `POST /v1/auth/login-requests`.
   - Validate:
     - project exists
     - request `Origin` is registered for the project
     - requested `redirectUri` exactly matches a registered redirect URI for the project
   - Add hosted login entry on `auth.celeris.pro`, for example:
     - `GET /auth/login?loginRequestId=...`
   - After Privy login succeeds on the hosted auth origin:
     - verify the Privy-authenticated identity
     - upsert `celeris_user`
     - upsert `project_user`
     - issue a one-time auth code or equivalently short-lived handoff artifact
   - Prefer returning an auth code to the opener and exchanging it for session tokens over returning a long-lived session token directly from the popup.

5. Rewrite player API auth to trust Celeris sessions.
   - Replace browser-facing player-route auth from raw Privy bearer tokens to Celeris-issued player session tokens.
   - Keep wallet principal resolution derived from the hosted auth gateway’s verified Privy identity.
   - Preserve app-level chain checks after the player session is resolved.
   - Privy verification should become an internal auth-gateway concern for web login, not the per-request browser API contract.

6. Rewrite the browser SDK around `celeris.login()`.
   - Add login helpers that:
     - create a login request
     - open the hosted auth popup on `https://auth.celeris.pro`
     - listen for a completion message from the hosted auth origin
     - exchange the one-time code for a player session
   - Validate popup completion with exact origin checks.
   - Add logout / session-clear helpers as needed.
   - Keep player API methods scoped to the authenticated player session.

7. Rewrite the standalone player demo and bootstrap flow.
   - `mock-game-frontend` must use hosted Celeris login rather than any direct Privy-token assumption.
   - `scripts/mock-game-frontend.ts` and `scripts/full-demo.ts` must bootstrap:
     - hosted auth origin
     - project allowed origins
     - project allowed redirect URIs
   - Any copy that implies a developer frontend must be allowlisted directly in Privy should be removed.

8. Add exact origin and redirect security checks.
   - `Origin` checks must use normalized exact origin matching, not substring matching.
   - `redirectUri` validation must require exact matches against registered URIs.
   - Popup completion must post back only to the validated developer origin.
   - Expired or consumed login requests and auth codes must fail closed.

9. Rewrite tests and docs.
   - Add tests for:
     - allowed-origin enforcement
     - redirect-URI enforcement
     - popup completion validation
     - session issuance
     - shared `celeris_user` plus app/project-scoped membership
   - Rewrite prior browser auth expectations so developer frontends no longer depend on direct Privy bearer tokens.

## Acceptance Criteria

- A developer frontend can authenticate a player through `celeris.login()` without embedding Privy directly on the developer origin.
- The hosted login UI runs on `https://auth.celeris.pro`.
- Login initiation is rejected when:
  - `projectId` does not exist
  - request `Origin` is not registered for the project
  - `redirectUri` is not registered for the project
- Privy login for browser flows occurs only on the Celeris-controlled auth origin.
- The browser player API uses Celeris-issued player session tokens rather than raw Privy tokens.
- The same wallet-backed player resolves to one shared `celeris_user` across projects/apps.
- App/project-scoped membership remains distinct per project/app.
- Developers do not need their origins allowlisted in Privy just to use browser login through Celeris.

## Unit Test Cases

- Login-request creation rejects unknown `projectId`.
- Login-request creation rejects an unregistered request `Origin`.
- Login-request creation rejects an unregistered `redirectUri`.
- Hosted login completion rejects expired or consumed login requests.
- Popup completion only accepts messages from `https://auth.celeris.pro`.
- Player-session verification resolves wallet principal and shared player identity correctly.

## Integration Test Cases

- Browser SDK creates a login request, opens hosted login, exchanges the returned auth code, and can then call `GET /v1/me`.
- A developer frontend on an unregistered origin cannot initiate login.
- A developer frontend requesting an unregistered redirect URI cannot initiate login.
- One wallet can log into two different projects/apps and produce:
  - one shared `celeris_user`
  - two distinct app/project membership records
- The standalone demo can authenticate through the hosted auth gateway and then execute the existing wallet-keyed player flows.
