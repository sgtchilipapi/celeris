# WO-05.5 Celeris-Owned Privy And Shared Identity

## Objective

Pivot the updated MVP from developer-supplied Privy app ownership to a single Celeris-owned Privy app that backs player authentication across all Celeris apps.

This work order preserves the wallet-native player model established in earlier work orders while changing who owns the identity boundary.

The target model after this WO is:

- Celeris owns the Privy app configuration used for player auth
- player identity is shared across all Celeris apps
- wallet address remains the product-level player principal
- app-scoped ownership still happens through `(appId, chainId, walletAddress)`
- developers no longer configure or supply `privyAppId`

## Scope

In scope:

- removal of per-app `privyAppId` from developer-facing contracts
- introduction of platform-owned Privy runtime configuration
- preservation of app-level chain policy
- shared player identity semantics across apps
- dashboard and demo updates needed to match the new auth-ownership model

Out of scope:

- replacing Privy with a different identity provider
- changing wallet-keyed ledger and payment behavior
- changing managed action or asset-delivery semantics
- developer bearer auth and server SDK work beyond the contract changes required to unblock `WO-06`

## Implementation Steps

1. Replace the public auth-ownership contract in `celeris/types.ts`.
   - Remove `privyAppId` from app create/update/setup payloads.
   - Replace the current app auth contract with an app-level player policy contract that keeps only fields still owned per app.
   - Keep `allowedChainId` app-scoped unless there is an explicit decision to centralize chain policy too.
   - Introduce an internal platform-owned Privy config contract for runtime bootstrap.

2. Rewrite schema and in-memory storage.
   - Remove any storage concept whose primary purpose is to persist per-app Privy ownership.
   - If a separate app policy table or map remains, it must represent app execution policy, not external auth ownership.
   - Keep enough app-level data to enforce chain restrictions and to describe player compatibility to clients.

3. Rewrite app creation, update, and setup flows.
   - `POST /apps` and `PUT /apps/:appId` must stop accepting `privyAppId`.
   - App setup and catalog responses must stop exposing developer-supplied Privy app ownership fields.
   - The developer dashboard must stop rendering `Privy App ID` as an app-managed field.

4. Rewrite player auth bootstrap around platform-owned Privy config.
   - Load the single Privy app configuration from Celeris runtime config or environment.
   - Verify player bearer tokens against the shared Celeris-owned Privy configuration.
   - Preserve app-level chain checks after token verification.
   - Keep the wallet-derived subject mapping shared across apps rather than reintroducing app-local player identities.

5. Rewrite frontend and demo bootstrap assumptions.
   - `mock-game-frontend` must no longer require per-app Privy ownership config from app setup.
   - `scripts/mock-game-frontend.ts` and `scripts/full-demo.ts` must source player-auth bootstrap from Celeris-owned config instead.
   - Any demo copy that implies “bring your own Privy app per game” must be removed.

6. Rewrite tests and docs.
   - Replace BYO-Privy expectations with platform-owned Privy expectations.
   - Add cross-app shared-identity coverage.
   - Update developer setup and dashboard tests to assert that `privyAppId` is absent from app-management contracts.

## Acceptance Criteria

- No developer-facing app contract accepts or returns per-app `privyAppId`.
- The runtime owns one shared Privy configuration for player authentication.
- The same authenticated wallet principal can access multiple Celeris apps without separate player identity creation.
- App-level wallet ownership remains scoped by `(appId, chainId, walletAddress)`.
- App-level chain restrictions are still enforced after authentication.
- Dashboard and demo surfaces no longer imply that each developer brings their own Privy app.
- `WO-06` can proceed against a stable Celeris-owned auth contract.

## Unit Test Cases

- `PrivyAuthService` resolves the same wallet principal independently of which app route is being called.
- App creation and update contracts persist `allowedChainId` without persisting a developer-supplied `privyAppId`.
- App setup serialization exposes app-level player policy fields only.
- Platform auth bootstrap fails closed when the Celeris-owned Privy runtime config is missing or invalid.

## Integration Test Cases

- A single authenticated wallet can call player routes against two different apps and receive app-scoped balances under one shared identity.
- A wallet token valid for the platform is still rejected when an app’s `allowedChainId` does not match the wallet chain.
- Dashboard integration tests can create and edit apps without any `Privy App ID` field.
- `mock-game-frontend` and `start:full-demo` boot without requiring per-app Privy ownership arguments.
